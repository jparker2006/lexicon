## Summary

A stuck mic start can no longer lose a Dictation silently. The engine gets 2 s to start. After that the Dictation ends with the "Microphone unavailable" notice and a `failed` row. The stuck queue is abandoned, and the next fn-down builds on a fresh one. The History row is recorded at fn-down, while the mic starts.

```diff
 Conductor.run (fn-down)
-  context = await destination.context()   // in parallel with the start below
-  capture = await recorder.start(...)       // no limit: a stuck Core Audio call hangs here forever
-  history.record(.began)
+  async let began = beginRow()              // context, then .began: never waits on the mic
+  capture = await recorder.start(...)       // throws .startTimedOut
+    catch -> startFailed: end the slot (a stop, so the pill leaves "recording"),
+             .failed row (.discarded for a stray tap), microphoneUnavailable notice

 Microphone.start
+  if permission reads undetermined
+    requestRecordPermission(), up to 60 s for Jake to answer; the answer is remembered
+  within 2 s: begin on the current MicLane's queue
+    late success -> cutOff (the engine is stopped, never left holding the mic)
+    timeout      -> abandon the lane, make a new MicLane, throw .startTimedOut
```

`Microphone` is now a thin front over `MicLane` (one queue, its prepared and active engine). New locks: `Mutex<MicLane>` (swapped from the deadline task), the reply `Mutex` in `within` (first answer wins), `MicLane.abandoned` (release/acquire: a stale lane starts nothing), `MicPermission` (Jake's answer, written from the prompt task).

From Live checks: macOS holds an engine start while its Allow prompt is up, so the prompt is asked for first, outside the limit. After a re-grant macOS can keep reporting "undetermined" in-process, which left every engine cold, so Jake's answer is kept per process.

## Merge Danger

**Door:** two-way

**Blast Radius:** mic start

- The wedge didn't reproduce live (the lead: daily and Dev opening the input for one press). Whether a fresh queue escapes Core Audio's stuck call is unproven. If not, every fn-down fails at 2 s with a notice and a row, never silently, and each leaves one blocked thread until relaunch.
- A start slower than 2 s fails the Dictation (cold starts measured 74 to 212 ms in #52).
- A fn-down made within 2 s of an earlier stuck one queues on the stuck lane and fails with its own notice. The next press after the notice gets the fresh lane.
- Every failed mic start now leaves a `failed` row (`microphone: <error>`), no permission and no device included. Play flashes "No audio" and Retry does nothing, as for a file lost to a crash.
- With fn still down at the limit, the pill plays the stop sound, then shows the notice.
- Later: a device-change rebuild stuck mid-Dictation still has no limit (pre-existing). A reset after an in-process Allow that macOS doesn't report reads as allowed.
- Merge order: no textual overlap with open PRs. Land before #138: its grant-time `recorder.prepare` then runs under the limit.
